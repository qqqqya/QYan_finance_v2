## 1. 字段与数据库映射

顶层固定包含 format、schemaVersion、appVersion、exportedAt、currency、timeZone、data、checksum。数据库版本为 2，备份协议版本仍为 1，两者分别维护。

checksum 固定为 algorithm: SHA-256、value: 64 位小写十六进制。计算时移除顶层 checksum，递归按 UTF-16 键序排序对象键，数组保持原顺序，再对紧凑 JSON 的 UTF-8 字节计算 SHA-256。文档 03、应用校验器、带有效校验和的最小样例使用同一约定。修改任何数据后必须重新计算校验和；它不提供加密或身份认证。

| 集合/对象 | 映射与规则 |
|---|---|
| projects | 项目类型 asset/liability/income_log/expense_log；名称使用 nameKey 或 customName；includeInSummary、sortOrder 均保留 |
| balanceRecords | 整数 balanceMinor；以 projectId 关联资产或负债；businessDate、businessTime、orderKey 一起决定先后 |
| projectEntries | 整数 amountMinor；仅关联独立收支项目，方向由项目类型决定 |
| bills | 收入/支出、整数 amountMinor、categoryId、业务时间、备注；没有资产账户关联字段 |
| categories | 收入/支出方向、名称键/自定义名称、排序、isActive |
| memos | 标题、正文、业务日期、tags 字符串列表；数据库内部 tagsJson 在备份中还原为数组 |
| editHistory | entityType、entityId、changedAt、before、after；数据库内部 JSON 字符串在备份中还原为对象 |
| settings | themeMode：system/light/dark；languageMode：system/zh-Hans/zh-Hant/en；currency：CNY；timeZone：IANA 时区标识 |

业务对象的 createdAt/updatedAt 以及历史 changedAt 使用 UTC ISO 8601（以 Z 结尾）。数据库内部以毫秒整数存储，导出时转成字符串，不丢毫秒精度。业务日期为 YYYY-MM-DD、时间为 HH:mm，不使用 UTC 创建时间替代业务日期。

阶段 3 的账单修改历史在 before/after 中额外保留 categoryNameKey、categoryCustomName 名称快照，以便分类迁移删除后仍显示原分类；历史快照内的旧 categoryId 不作为当前业务外键校验。备忘录历史使用 tags 数组，不使用数据库内部的 tagsJson 字符串。正式备份往返应原样保留这些历史字段，协议仍为 v1。

所有金额都是整数分。余额允许 0；收支必须大于 0；单条上限为 999999999999 分。不导出当前余额、变化额、总资产或图表等推导缓存。

项目分类以 categoryKey 保存。内置分类使用 bank 等固定键；阶段 2 的自定义分类使用 `custom:<用户原文>`，例如 `custom:bank`，显示时仅去掉一层前缀，不翻译用户原文。原文最长 80 字符；仍兼容既有未知分类键按原文显示。备份往返必须保留前缀，不能将自定义文本误当内置键翻译；字段类型与协议版本不变。

## 2. Schema 之外的业务校验

JSON Schema 验证字段类型与形状；应用校验器还验证：

- UUID 唯一、父子引用存在、余额/流水对应项目类型、账单与分类方向一致。
- 同项目 orderKey 唯一，名称不能仅含空白；业务时间有效且不晚于账本当前时间。
- 顶层币种和时区与 settings 一致；时区能被应用的时区库识别。
- 修改历史关联对象存在；before/after 的金额字段同样使用整数分。
- 导入资源限制、版本迁移和往返一致性，按文档 03 执行。

导入与导出使用相同上限：UTF-8 最大 32 MiB，七类业务集合合计最多 100,000 条；历史对象最多 24 层。未知字段、缺失字段和不支持的协议版本拒绝；不猜测无校验和的旧 JSON。文件扩展名只为方便识别，内容才决定格式。

恢复采用完整替换，不做合并，不依据文件名猜测格式，不把 URI 当磁盘路径。校验和确认前不写业务库。最近一次覆盖前的完整数据保存在 SQLite 辅助表 local_data_states.recovery_json，与整体替换在同一事务提交；失败和中断保持原数据及原副本，成功后才发布查询更新。恢复私有副本同样预览确认，成功后将本次覆盖前的数据保存为新副本。只保留一个副本，可单独删除。

辅助表还保存最近成功导出的名称、URI、位置、大小、时间，以及恢复出厂的待清缓存标记；这些是设备操作状态，不进入备份，避免递归副本及跨设备失效路径。恢复出厂在事务中清空业务、历史、设置和副本并重新生成九个零金额默认项目；提交后清理私有分享缓存及 URI 授权，中断时下次启动重试。外部导出文件不删除。

## 3. Android 文件与分享

导出使用 ACTION_CREATE_DOCUMENT；写流关闭后重新读取，比对字节数和 SHA-256，验证成功才显示成功。导入使用 ACTION_OPEN_DOCUMENT，读取 content URI，不申请全盘文件访问权限。取消不显示成功，也不改变数据。写入失败尝试删除本次新建的残缺文件，持久化日志供下次启动补清理。

系统可调整重名文件名，成功弹窗显示提供器返回的实际名称、大小和可获得的位置；不能获得具体目录时显示提供器信息。分享复制到受限私有缓存，通过 FileProvider 的 content URI 和临时只读授权调用系统分享面板。面板打开不表示对方已收取。分享缓存保留至多 24 小时、最多 10 份；恢复出厂清除。最近备份仅记录最后一次实际成功导出，不是所有外部文件的扫描列表。

官方机制：[Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files)、[安全文件分享](https://developer.android.com/training/secure-file-sharing)。正常同包名、同签名且版本允许的 APK 覆盖升级由 SQLite 增量迁移保留数据；卸载会清除私有数据库和恢复副本，需提前导出到外部位置。

## 4. 检查方式

在 PowerShell 7 中执行：

```powershell
.\scripts\check-backup.ps1
```

该脚本仅验证 Schema 与小数“分”拒绝规则。校验和、业务引用、事务、恢复出厂与往返另由 test/data/backup_workflow_test.dart、backup_resource_test.dart 和 test/backup_widgets_test.dart 验证；真实文件测试另见文档 11。
